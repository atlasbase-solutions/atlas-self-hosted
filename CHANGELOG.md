# Changelog

All notable changes to the Atlas Self-Hosted distribution are documented here, newest release first. The version is the Atlas release number: Portal, Tracking Gateway, the migrator, the operator tools, the Portal SPA and the edge image are one release unit and always carry the same number. `UPGRADE.md` lists the supported source versions and the upgrade steps of each release.

Version 1.0.9 is the first public release of this repository. Its section lists every customer-facing change made since the 1.0.0 baseline, so that an installation made from an earlier private build can see everything it is about to receive.

## 1.0.9 — 2026-09-28

### Security

- License checks are stricter: a portal domain that does not match the license now stops the portal's application API, and the screen names the reason.
- The link check available on a fresh installation no longer accepts postbacks; run end-to-end conversion tests through a licensed tracking domain.
- The reputation-data endpoint is now built into Portal as `https://antifraud.getatlasbase.com` and can no longer be changed by configuration; `PORTAL_ANTIFRAUD_FEED_URL` is ignored and Portal logs a warning when it is set.
- Access checks now look at the person and the object, not only at the role, and the public API applies the same check as the portal. An advertiser can still see every partner working with their offers but can change only their own private partners; a shared network partner's profile, status, logins, team, invitations, logo and tracking links are no longer editable from the advertiser's cabinet. A payout statement is sent to the address on the partner's card, and only network staff can enter another recipient. A manager without finance access can no longer confirm or cancel payouts through the API, and a partner's team member who is not the main login can no longer change payment details there. Network-wide payout totals and revenue-share breakdowns are shown only to network staff. The advertiser's partner list and a shared partner's card no longer fail to open because of missing labels. Sign-in takes the same time for known and unknown addresses, the staff directory no longer searches by email, and server errors no longer include internal database messages.
- The tracking host now publishes the intake routes only — clicks, landing-page clicks, impressions, postbacks, the public refusal preview, `/health/*` and `/version` — and answers 404 to anything else. The tracking service's Prometheus metrics moved from the public port to a separate internal address (`METRICS_ADDR`, `:9108` by default), so traffic volumes, refusal rates and anti-fraud signals are no longer reachable from the internet. Readiness and startup answer from outside with a status only, with the reason in the service log, and the edge writes postback log lines without the query string that carries the receiver's token. The edge now sets the forwarding headers itself: a header from a client is replaced unless it comes from the proxy subnet you named.
- A service no longer starts with a secret left from the configuration example or with a weak encryption key. Any value carrying the `CHANGE_ME` marker — including a password inside a database URL — is refused, and the encryption keys `PORTAL_SECRET_KEY` and `ATLAS_CONFIG_SECRET_KEY` must now be exactly 32 random bytes in hex or base64 instead of a passphrase of any length. The initial owner password from `PORTAL_OWNER_PASSWORD` is checked against the password policy and has to be replaced at the first sign-in. `PORTAL_SESSION_SECRET` protected nothing and has been removed.
- Outbound requests to an address entered in the portal — postbacks, conversions returned to a traffic source, the receiver test event and the SMTP server — now go only to globally routable unicast addresses. Carrier-grade NAT (`100.64.0.0/10`, used by Tailscale, Kubernetes and some cloud metadata services), benchmark, documentation and reserved ranges, and NAT64/6to4/Teredo addresses embedding an internal IPv4 are refused as well. The receiver test event no longer shows the network error text and shows a response only from an allowed address; a return address written as an internal IP is refused when saved. An SMTP server on a port other than 25, 465, 587 or 2525 is reachable only inside a subnet the operator allowed.
- A postback no longer writes anything before its token is checked. A partner could previously bind any player to themselves, and take the player's lifetime revenue share, by sending a postback with no token; the player binding is now stored only after the token (and, in strict mode, the signature) is accepted. A postback that matches no click, player or promo code now answers `401` unless it carries a valid token, the same as a postback with a wrong token, so the response no longer reveals which click IDs, players or promo codes exist. Look up the reason in Analytics by the `X-Atlas-Request-Id` header. New and cloned offers are created in Observation mode with both a postback token and a signing key, shown once right after creation. The postback tab shows the share of correctly signed postbacks over the last 7 days and offers to switch to strict mode once all of them are signed.
- Releases are signed with a dedicated Atlas release key. `atlas-update-check -verify <dir>` checks an unpacked distribution without a license or network access, and the installer runs that check before installing anything.
- An offline license file is now checked the same way as the license itself; the reason a file is not accepted is written to the startup log.
- `ATLAS_LICENSE_FILE` now accepts only an offline license file; a license string placed there is treated like `ATLAS_LICENSE_TOKEN`. Installations that mount the offline license file they were issued are not affected.
- Distributions are signed with the Atlas release key `rel2`, fingerprint `51fe2e81bd1cd484`. `atlas-update-check -verify` and the installer print the fingerprint of the key that signed the distribution; compare it with the one published in the README and in the Atlas documentation.

### Features

- Portal and Gateway now trust the production signing key of Atlas reputation packages, so an installation with the reputation-data subscription can receive and verify them. Packages signed by any other key are still rejected.
- The offer's Landings tab now shows the results of landing A/B rotation: clicks, conversions, conversion rate with its confidence range, payout and network revenue per click for every variant, and a plain verdict on whether the leader is really better or more traffic is needed. Weights are saved as one set, every change of the traffic split starts a new experiment that can be compared on its own, and the tab warns that partner-specific landings do not apply while rotation is on.
- Anti-fraud conversion rules can now catch registration farms: the new signal "Conversions of the same goal from address" counts conversions of one goal from the same visitor address within a window (IPv4 whole, IPv6 per /64 subnet), and the new "Conversion goal" signal narrows a rule to a goal picked from your offers. The visitor address is never stored: the tracking gateway turns it into a derived value at click time, before EU anonymisation, and the portal stores only a value derived again with your network's key; deleting links by an address now also removes these observations.
- The license check now also reports the domain names on which the installation received traffic, with a request count per name. No click, conversion or visitor data is sent, and an isolated installation sends nothing.
- An installation without a confirmed license lets you paste the license on the portal screen shown before sign-in, with the installation's domains, ID and version ready to copy for your Atlas account manager. The Network Owner can replace, restore or remove the license in Settings → License, which also shows where the license comes from and whether traffic intake has confirmed it.
- The license can be installed from the portal: pasted on the activation screen of an installation that is not yet activated, and replaced, restored or removed by the Network Owner in Settings → License. It is stored in the file named by `ATLAS_LICENSE_TOKEN_FILE` and takes effect without a restart. `ATLAS_LICENSE_TOKEN` in the configuration still takes precedence, and the new optional `PORTAL_GATEWAY_INTERNAL_URL` tells the portal where to read the tracking gateway's state (default `http://gateway:9108`).
- Portal and Gateway accept the license from a file named by the new optional `ATLAS_LICENSE_TOKEN_FILE` variable; a new or replaced license takes effect without a restart. `ATLAS_LICENSE_TOKEN` still wins when both are set.
- The Docker Compose stack gains an `atlas-license` volume that holds the license installed from the portal, so an installation can be activated on the screen before sign-in and its license replaced, restored or removed in Settings → License, with no environment edit and no restart. A license set in `ATLAS_LICENSE_TOKEN` keeps working exactly as before and takes precedence over the volume.
- The first-run wizard now keeps the owner's answer to "Send certificate expiry notices to the owner's email" (checked by default), and the edge receives the owner's address for its certificate authority account once the owner exists. Installations configured through environment variables give the certificate authority no address.
- An installation set up in the first-run wizard no longer needs `PORTAL_APP_URL` or `PORTAL_TRACKING_DOMAIN`: links in emails lead to `https://<portal domain>` and partner links and postback addresses use the tracking and postback domains entered in the wizard. Values already set in the env files still win.
- An installation in setup mode now serves the first-run wizard API: the network name and time zone, the domains (each checked by fetching a one-time label through the domain itself), the certificate status and, over HTTPS on the portal domain only, the creation of the first network owner, which closes the wizard for good and is recorded in the activity log. The portal can publish its domains to the gateway and the edge through an `installation.json` file (`ATLAS_INSTALLATION_FILE`); domains set in the configuration always win over the wizard, and existing installations need no changes.
- A new installation without users now opens the first-run wizard in the browser: enter the setup code, name the network, add the portal and tracking domains (with DNS records to copy and a live check of each domain and its certificate), create the network owner over HTTPS on the portal domain, then activate the license and set up email or skip those steps. Any page of such an installation leads to the wizard, and once the owner exists the wizard is closed for good.
- `PORTAL_OWNER_EMAIL` and `PORTAL_OWNER_PASSWORD` are now optional: set both to have the first Network Owner created at startup as before, or leave both unset and the portal starts in setup mode, waiting for the first-run wizard to create the owner. The new `atlas-setup-code` command issues the one-time setup code that opens the wizard; only a hash of the code is stored, and a new code replaces the previous one.
- The edge of the Docker Compose distribution is now Caddy instead of nginx. In the new default `direct` mode it listens on ports 80 and 443 and obtains and renews TLS certificates for the portal and tracking domains itself, serves the first-run wizard by IP until setup is complete and answers 404 to IP addresses and unknown names afterwards; the `proxy` mode keeps the previous behaviour behind your own TLS proxy or load balancer. Domains entered in the wizard reach the edge without a restart, and the published routes are unchanged.
- The one-line installer asks no questions: it prepares the server, starts Atlas and saves a link with a one-time setup code to `/root/atlas-setup.txt`, and the network, domains, owner account and license are entered in the browser, in the first-run wizard. The same command works as cloud-init user data; `sudo atlas-setup-code` issues a new code if the link is lost. The installer no longer prints an owner password.
- The dashboard now opens in the network's timezone, labelled "network time", and remembers another timezone you choose in this browser. The filter row shows live traffic for the last 15 minutes next to how much is usual at this time, the activity chart draws clicks and conversions as two panels sharing one time axis with the weekday and CR in its tooltip, and the first tab is named in your language. Customize mode keeps widgets showing their data: each widget has a ⋯ menu to configure, move or remove it, and its title, date range, width and height are set in a side panel, where the date range is offered only to widgets that use it. The stats API adds `baseline_clicks` and `baseline_conversions` to the live counter, and `/api/me` returns `network_timezone`.
- The dashboard's first screen for the network owner and managers now opens with the period's traffic and a new "Network money" row — network revenue, partner payouts, margin and margin percentage, with currencies never added together — followed by the activity chart, the "Needs attention" summary, offers and partners. The summary now also flags network traffic that fell below half or rose above three times its weekly norm, offers whose conversion rate halved, partners who stopped sending traffic after a steady week and open fraud investigations; self-hosted owners get a reminder a month before the license ends. Changes against the previous period are shown as percentages only when the previous period had enough data (otherwise the previous value is shown), in percentage points for rates, and coloured by whether the change is good or bad. Transaction amounts carry their currency, and the stats API adds `transaction_amount_by_currency`. Existing dashboards keep their layout; press Reset in Customize to get the new set. On phones the period becomes a drop-down and wide tables show that they scroll.

### Fixes

- Browser password managers now save a new password together with the sign-in email on the invitation, password reset and forced password change screens. The email field on the invitation screens is read-only instead of disabled, so the browser no longer stores the password under an empty user name.
- The Flow dimension in Analytics now shows flow names instead of raw numbers, and a report can be narrowed to a single flow — the Flows list links straight into it. Rule errors in the Flows editor are shown in the portal's language and name the section and row they belong to, instead of an English sentence. A new filter now defaults to sending traffic to the fallback chain rather than silently discarding it, activating a flow whose every offer is stopped is refused, and the Flows screen gained paging, a mode filter and the same layout as the rest of the portal.
- In isolated mode (`ATLAS_LICENSE_ISOLATED=true`) the installation no longer contacts Atlas for anti-fraud reputation packages or telemetry. Packages already downloaded keep working.
- The public API contract now lists the `antifraud` value of `status_source` (and of `source` in a conversion's status history) together with the anti-fraud reason codes of `status_reason_code`. The API already returned these values, so a client that validated the enums strictly could fail on a real response. The codes are returned only to the network's own staff; publisher and advertiser keys keep receiving the outcome without the reason.
- The click passport in Analytics now reads "Sent to the fallback URL" in Russian, Spanish and Portuguese instead of an untranslated "Fallback". The build's translation check now also covers the Russian dictionary, so an English string left in the Russian interface fails the build.
- A fresh installation with `PORTAL_OWNER_EMAIL` and `PORTAL_OWNER_PASSWORD` set starts again: creating that first owner no longer fails with a database constraint error that kept the portal from starting. The seeded password still has to be replaced at the first sign-in and does not expire before it.
- The tracking gateway now recognises clicks from 54 cloud and hosting networks (AWS, Google Cloud, Azure, Hetzner, OVH, DigitalOcean and others) as datacenter traffic: such a click is marked as a bot, is not counted as unique, does not use caps or the traffic quota and is not paid per click. The list shipped before held only a test entry, so the datacenter signal never fired. Networks through which real people browse, such as iCloud Private Relay and Cloudflare WARP, are not on the list. Expect fewer unique and paid clicks from offers that received server traffic.
- `atlas-update-check`, the installer's signature check and the `-dry-run` help of `atlas-rotate-secrets` now speak English, like the rest of the operator tooling, and `atlas-update-check -help` prints its usage. The description of the anti-fraud blocked-clicks metric and one portal log message were translated as well.

### Operations

- The portal, the gateway and the edge are built with Go 1.27.1 and Node.js 24.21 LTS, with all Go and frontend dependencies updated to their latest releases; the bundled PostgreSQL, Redis and ClickHouse images move to their latest patch releases (18.6, 8.8.3, 26.6.8) and the edge to Caddy 2.11.
